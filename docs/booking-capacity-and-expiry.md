# 预约上限与待确认订单自动失效

## 数据流和跨端兼容

| 生产者 | 契约 | 消费者 |
| --- | --- | --- |
| 小程序确认页 `pages/confirm/confirm.js` | `POST /api/bookings`。现有店铺、理发师、服务、开始时间、预期原价和实付金额，及可选优惠券、备注字段继续使用。旧客户端省略预期金额也可建单。 | 后端 `src/routes/client-bookings.js` |
| 后端建单事务 | 每账号默认最多 5 个 `pending` 或 `accepted` 订单。超限沿用 HTTP 409 和 `{ message }`。`UserPolicy.bookingCreationFence` 仅供 MongoDB 事务串行化，默认投影隐藏。 | 小程序确认页在 409 时刷新优惠券并展示提示。商家 no-show 响应中的 `userPolicy` 保持原结构。 |
| 后端定时任务和商家订单操作 | 定时任务每 15 分钟扫描。开始时间已到或创建超过时限的 `pending` 转为现有的 `rejected`，使用既有拒绝原因和双端提示字段、`reject` 站内消息及 `booking.updated` 事件。优惠券恢复可用，订单实付恢复原价，占位释放。 | 小程序订单列表、详情、消息和首页会显示或刷新。商家端订单仓库及订单页处理已有状态和 WebSocket 刷新，后台订单列表使用同一订单结构。 |
| 小程序取消订单、商家接单和改期 | 继续使用现有请求。自动失效按状态及扫描时的开始时间做条件更新，订单、优惠券、占位和消息在一个事务内提交。 | 后端预约和商家路由、定时任务。 |

`MAX_ACTIVE_BOOKINGS_PER_USER` 默认 5。历史账号已经超限时，现有订单继续处理，低于上限后可以再次建单。`PENDING_BOOKING_TIMEOUT_HOURS` 默认 24，设为 0 只关闭按创建时长失效，开始时间已到的待确认订单仍会失效。数据库内部字段按建单逐步写入，既有策略记录无需回填。公开请求和响应沿用现有字段、类型和值，不需要客户端迁移或同步发布。

## 部署和回滚

1. 在生产只读统计符合实际配置的待失效订单。负责人确认数量和首次运行将为每笔订单生成一条站内消息后，按 Git 部署流程发布后端。
2. 检查运行配置、健康和就绪状态，核对首轮任务日志、订单变化与消息。单独核对移除静态路由前的旧图片存量。
3. 回滚后端提交可停止后续自动失效和上限判断。内部计数字段可留在库中，旧代码会忽略它。已失效的订单、释放的时段或优惠券和已生成的消息不会随代码回滚，恢复个别订单前需核实对应资源是否已被再次使用。
